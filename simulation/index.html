How it works

The five steps
  1. sender.py sends UDP packets seq,timestamp from h1 to h2.
  2. Switches only follow flow rules: s1 sends h1 traffic out s1-eth2 (via s2) until told otherwise.
  3. receiver.py keeps the next expected number. A bigger number than expected means the numbers in between are lost.
  4. Every 50 sequence numbers it works out loss %. Above the threshold it alerts the controller.
  5. The controller rewrites two rules: s1 eth1→eth3 and s4 eth3→eth2. Traffic now uses s3.
Two ways the controller finds out

Link failure: the switch sends an OpenFlow PortStatus message (LINK_DOWN) and the controller reacts. Packet loss on a link that is still up: only the application can see it, so the receiver writes an alert file that the controller checks every second.

Why UDP, not TCP?

UDP has no acknowledgements or retransmission, so lost packets stay lost and the application can count them. TCP would resend them and hide the loss.

Why fixed port rules and no flooding?

The topology has a loop (s1, s2, s4, s3). Flooding would circle forever and cause a broadcast storm. The controller installs rules ahead of time (proactive), so no packet waits for the controller (reactive PacketIn).

Why does the receiver go quiet before it reports loss?

A gap is only known when a higher sequence number arrives. While the link is down nothing arrives, so the loss shows up after the first packet on the new path.

Limitations
  • No failback: after rerouting, traffic stays on the backup path.
  • One backup path and a fixed topology.
  • The alert goes through a file, so the controller reacts up to a second later.
  • The loss threshold avoids rerouting on one or two random drops.
